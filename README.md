# Leadora

把内容准备、发布、设备管理和多账号互动放到一个工作台里。

我做这个项目，是想减少内容运营过程中反复切换页面、重复设置和手动核对结果的操作。内容准备好了，要能接到发布；账号与设备的状态，要能对应到实际操作；AI 起草了一条回复，也要能看清回复对象和处理结果。

项目已有实际功能实现和正式环境部署记录，目前仍在完善使用流程与稳定性。最近一批工作集中在回复设置、训练与资料的衔接、评论草稿和历史处理记录。

## 我负责什么

我主要负责需求拆解、交互定义、功能优先级、真实使用反馈和验收要求。技术实现通过 AI 编码工具协作推进，我持续核对需求、交互和实际结果能否对应。

我在迭代中反复关注三个问题：

- 设置改了以后，用户能不能知道保存状态和生效范围。
- 页面选中的对象，是否就是实际处理的对象。
- 界面说处理完成时，能不能找到对应记录并核对结果。

## 开发过程

- 拆解内容准备、发布与运营中的重复操作。
- 整理功能之间的共同需求，减少不同入口各自维护一套逻辑。
- 根据使用反馈调整交互、状态提示与设置反馈。
- 核对规则、执行结果与处理记录，并持续补齐稳定性问题。

## 最近三个问题怎么处理

| 原来的问题 | 产品要求与协作实现 |
| --- | --- |
| 回复设置缺少清楚的反馈，不同账号的规则容易对不上。 | 明确通用规则与账号例外；显示修改和保存状态；训练读取实际生效的规则。 |
| 评论中有多人互动，后台任务可能干扰正在编辑的回复。 | 点击评论选择回复对象；草稿对应选中的评论；人工修改的内容需要保留。 |
| 记录列表看得到，但较早的记录和对应消息难以找到。 | 分页查询当前可访问浏览器账号的历史处理记录；选中记录时定位到对应消息。 |

## 技术栈

Python、JavaScript、SQLite、桌面客户端与 Android 设备接入。

## 当前阶段

最近一批改动已有正式加载、相关回归及实际网页检查记录。跨通道发送额度、从评论发起首次私信、完整作品同步和真实多账号发送验收仍在补齐；SaaS 迁移暂缓。

每个模块的进度分别说明，避免把一次局部检查当成整个软件已完成验收。未发布未经核实的客户规模、商业收益或效率提升数字。

## 这些记录如何使用

开发记录根据私有工程的提交与留存文档整理；案例区分产品要求、已实现变化和已验证范围。它们用于说明产品工作过程。软件现场运行情况可在面试时另行演示。

本仓库只公开文字说明与经过核对的开发记录。软件界面、源码、账号、客户记录、作品素材和部署配置不在本仓库中。
